# PDF local server

The Node process is separate from `PDF.exe`. It listens only on
`127.0.0.1:8000`. The desktop application remains windowless, counts presses
only, and uploads its count file every five minutes. It never records typed text.

## Start

Install Node.js **22.13 or newer**, including npm; Node 24 LTS is recommended.
SQLite uses Node's built-in `node:sqlite`, so no SQLite npm addon, database service,
Python, compiler or other runtime dependency is needed. Node 22.14 prints an
experimental SQLite warning; it does not prevent startup.

```powershell
cd D:\omerapp\server
npm.cmd ci
npm.cmd start
```

Keep the terminal running. Stop with Ctrl+C. The server does not register itself
for automatic startup or modify the desktop installer.

First start automatically creates `D:\omerapp\server\database.sqlite`, the
`uploads` and `appsetup` tables, and `D:\omerapp\server\uploads\` if absent.
SQLite may create `database.sqlite-wal` and `database.sqlite-shm` beside the database
while running. All persistent data stays in this server directory, regardless
of the shell's current directory.

## Admin and setup download

Open **http://127.0.0.1:8000/admin**. Choose the rebuilt
`D:\omerapp\dist\PDF-Setup.exe` and click **Upload setup**. The `appsetup` table
stores metadata and a relative path to a uniquely named executable in `uploads/`;
the executable itself is not stored as a SQLite BLOB. It has a single current row
(`id=1`). A replacement is committed before the old setup is removed.

Open **http://127.0.0.1:8000/** to attempt an automatic download without an initial
click. A visible manual link remains available if browser download policy blocks
the attempt. The filename sent to the browser is `PDF-Setup.exe`. With no setup,
or a setup whose backing file is missing, the page displays **No file available.**
Serving/downloading an upload never executes it.

The admin table lists received text files newest first. **Open** displays inert
UTF-8 plain text in a new tab. **Download** saves the original filename. **Delete**
asks for confirmation, then removes the stored file and its SQLite row. Missing
files give a clear 404; a stale row can still be deleted. Refresh updates the list.

The **Device** column displays the Windows device name, PDF device ID and Windows
version/build. The ID is generated by PDF and saved per user, independently of
hardware identifiers. Older clients and pre-update uploads display **Unknown
device**. Device labels are supplied by the client; they identify an installation
but do not authenticate its physical hardware.

## HTTP routes

| Method and route | Result |
| --- | --- |
| `POST /create` | One multipart UTF-8 `.txt` file in field `file`; HTTP 201 after both file and database row are saved |
| `GET /` | Minimal automatic-download page, or “No file available.” |
| `GET /download/app` | Current setup with attachment headers; HTTP 404 if absent |
| `GET /admin` | Admin page |
| `GET /api/uploads` | Received text metadata, newest first |
| `GET /api/uploads/:id/open` | Plain UTF-8 file contents |
| `GET /api/uploads/:id/download` | Original text as an attachment |
| `DELETE /api/uploads/:id` | Remove text file and row |
| `GET /api/appsetup` | Current setup metadata, or JSON `null` |
| `POST /api/appsetup` | Admin's multipart `PDF-Setup.exe`, field `file` |

Text files are limited to **5 MiB**, setup to **64 MiB**, with one file per request.
Count uploads may include three additional UTF-8 fields: `device_id` (UUID),
`device_name` (up to 255 characters) and `os_version` (up to 96 characters). Supply
all three together, or omit all three for an older client. Duplicate, unknown,
oversized and partial fields are rejected. Each field is limited to 1024 bytes.
Setup uploads still accept only the `file` field. UTF-8 file validation checks the actual bytes across stream boundaries,
rejecting malformed encoding, NUL and binary control characters. An empty UTF-8
file is valid. `application/octet-stream` is accepted from the native WinHTTP
client when the filename and bytes pass text validation; MIME labels alone are
not trusted. Setup must have the expected filename and a valid DOS/PE executable
header, and cannot be a DLL.

Invalid input returns HTTP 400 or 415; oversized files return 413; missing files
return 404; database/filesystem failures return 500. JSON errors contain an
`error` message. Successful uploads return `{"success":true,"upload":{...}}`.
Failed validation and database insertion remove their staged file. SQLite uses
FULL synchronous commits; each upload is flushed before its record is inserted.
Delete uses a SQLite transaction and a reversible file rename to restore the file
if the database operation fails.

Generated UUID filenames, parameterized SQL, strict numeric IDs and server-owned
paths prevent user-supplied paths from selecting files. Only the public frontend
is statically served; the database and uploads directory are not exposed as
static directories. Opened text uses `text/plain`, `nosniff` and a sandbox content
security policy. The admin is local only, without a login system; Host/Origin
checks reject DNS rebinding and cross-site browser changes. This is not a public
internet deployment.

The `uploads` columns are `id`, `original_name`, `stored_name`, `file_path`,
`file_size`, `received_at`, `device_id`, `device_name` and `os_version`. At startup,
the server adds missing device columns in a transaction, leaving existing rows,
IDs, setup metadata and uploaded files intact. Legacy rows have NULL device fields.
Dates use UTC ISO 8601. `appsetup` keeps its original file metadata and singleton
primary key, without device fields. The server acknowledges only committed
uploads. The client clears only the acknowledged prefix after HTTP 2xx, preserving
newer count records. Failures leave its installation-directory file for the next five-minute
attempt. Lost acknowledgments may produce duplicate records, preserving the
existing retry behavior.

## Verify

```powershell
cd D:\omerapp\server
npm.cmd test
npm.cmd run test:browser
npm.cmd audit
```

The server tests use isolated directories under `server/`, exercise all routes,
check stored file/row pairs, error cases, limits, missing files, concurrency and
database failures, then remove their own fixtures. They need the rebuilt
`D:\omerapp\dist\PDF-Setup.exe` for setup checks. For native WinHTTP integration,
first run `D:\omerapp\tests\Test-Upload.ps1` with the C++ toolchain as described in
the root README. This creates `build\upload_test.exe`; the last server test uses
it against a real Express listener on an automatically assigned loopback port.
Tests can run alongside your existing port 8000 server. If the native harness is
absent that test is explicitly skipped. The test harness alone accepts
`PDF_TEST_PORT`; the shipped desktop client always uses port 8000.

The optional browser test uses an installed Chrome or Edge and Node built-ins,
without additional npm dependencies. Set `PDF_TEST_BROWSER` to an alternate
browser executable if needed. It checks the admin form, list, open, download,
confirmation cancel/accept, responsive layout and automatic/manual setup download
requests. It reports canceled executable downloads as a browser limitation,
separately from HTTP integrity checks. Logs, JSON results and screenshots are
saved under `D:\omerapp\build\`.

To rebuild the desktop executable and installer, follow the root README. Client
multipart uploads are implemented in `D:\omerapp\src\http_upload.cpp` and device
information in `D:\omerapp\src\device_info.cpp`. Counting stays in
`D:\omerapp\src\keystroke_counter.cpp`. The count file on this machine is
`%LOCALAPPDATA%\Programs\PDF\yourtext.txt` for a normal installation; the client
resolves the directory containing `PDF.exe`, independently of its working directory.
